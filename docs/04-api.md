# API

Префикс `/api/v1`. Всё, кроме `auth/*`, справочника и `/health`, требует access-токена в
заголовке `Authorization: Bearer …`. Живая документация — `/docs` запущенного бэкенда,
схема — `/api/v1/openapi.json`.

## Соглашения

- Ответы только через Pydantic-схемы, ORM наружу не отдаётся.
- Ошибки в едином формате: `{"detail": {"code": "...", "message": "...", "fields": {...}}}`.
  `code` — машинный, `message` — на русском, для показа пользователю, `fields` — ошибки по
  полям формы. Ошибка валидации — 422, конфликт состояния (онбординг не завершён) — 409,
  недоступный внешний сервис (прогноз) — 503.
- Даты — ISO 8601 с таймзоной. Веса — килограммы, сериализуются строками для сохранения
  точности (`"17.50"`); обхваты — сантиметры строкой с одним знаком (`"82.5"`).
- Пагинация — `?page=&size=` (size до 100), ответ `Page[T]`: `items`, `total`, `page`,
  `size`, `pages`.
- Подходы, которые клиент может отправить повторно, идемпотентны по `client_uuid`.

## Аутентификация

```
POST /auth/register
POST /auth/login                    login — email или username; access в теле ответа
POST /auth/refresh                  refresh — из httpOnly-cookie, при каждом вызове ротируется
POST /auth/logout
GET  /auth/me
POST /auth/verify-email             токен из письма
POST /auth/verify-email/resend
POST /auth/password-reset/request
POST /auth/password-reset/confirm
```

Refresh-токен живёт в cookie `HttpOnly; SameSite=Strict; Path=/api/v1/auth`, в продакшене —
`Secure`. `login` и `register` ограничены по частоте на IP клиента (Redis); за прокси
реальный IP берётся из `X-Forwarded-For`.

`/users…` остались из шаблона: список и удаление — только суперпользователю, чтение — любому
вошедшему, правка — владельцу аккаунта или суперпользователю. Приложение ими не пользуется.

## Справочник

```
GET /exercises          фильтры: pattern, equipment (`none` — без оборудования),
                        difficulty_min, difficulty_max, location_id;
                        весь список без пагинации — справочник маленький
GET /exercises/{slug}
GET /patterns
GET /patterns/{code}/ladder     полная лестница сложности
GET /equipment                  каталог возможного оборудования
GET /skills
```

Справочник меняется только с деплоем: кеш в Redis и `ETag` (`If-None-Match` → 304).
Клиент держит его в кеше TanStack Query надолго. У упражнения есть `timed: true`, если оно
измеряется секундами работы, а не повторами.

`GET /exercises?location_id=` требует входа: учитываются инвентарь, ограничения места и теги
здоровья пользователя.

## Места и инвентарь

```
GET    /locations
POST   /locations
PATCH  /locations/{id}              в т.ч. geo_lat / geo_lon — только для уличных мест
DELETE /locations/{id}
PUT    /locations/{id}/equipment    полная замена инвентаря места
GET    /locations/{id}/weight-grid  доступные веса и минимальный шаг
POST   /locations/{id}/plates       разбивка целевого веса на блины
```

Координаты нужны для прогноза погоды. Сервер хранит их округлёнными до двух знаков (~1 км),
принимает только парой и только у `outdoor_gym` / `outdoor_bare`; `null` в обоих полях —
убрать отметку.

## Программа

```
POST /programs/preview              сгенерировать без сохранения (экран «вот что получилось»)
POST /programs                      создать и сделать активной
GET  /programs/active               404, если программы нет
GET  /programs/active/next-session  первый день активной программы без завершённой тренировки
GET  /programs/{id}
```

Тело `preview` и `POST /programs` — `{"day_locations": [id, ...]}`: место для каждого
тренировочного дня по порядку, длина равна `days_per_week`. Без него все дни в основном
месте. Дни порядковые, к дням недели не привязаны. Оба эндпоинта требуют завершённого
онбординга (иначе 409). `POST /programs` переводит прежнюю активную программу в `abandoned` —
так же делается и пересборка.

## Тренировка

```
POST /sessions                          старт тренировки
GET  /sessions                          история: ?status=in_progress|completed|aborted, пагинация
GET  /sessions/{id}
POST /sessions/{id}/sets                батч подходов, идемпотентно по client_uuid
POST /sessions/{id}/substitute          замена упражнения с причиной
POST /sessions/{id}/trim                пересборка под оставшееся время
POST /sessions/{id}/swap-location       перенос всей тренировки в другое место
POST /sessions/{id}/finish              {"note": "..."} — необязательно
POST /sessions/{id}/abort
```

**Старт.** Тело:

```json
{
  "planned_session_id": "…",       // день программы; без него — следующий по next-session
  "unplanned": false,              // true — свободная тренировка на всё тело вне программы
  "location_id": "…",              // где сегодня; без него — место дня, затем основное
  "readiness": {"sleep": "ok", "stress": "ok", "soreness": "ok"}   // bad | ok | good
}
```

Одновременно открыта только одна тренировка: старт новой закрывает предыдущую как
`aborted`. Найти открытую, чтобы продолжить, — `GET /sessions?status=in_progress&size=1`.

Ответ содержит тренировку, подготовленную движком: `blocks` (разминка и заминка — `drills`,
остальное — `exercises` с весом, целью, отдыхом, темпом и `hint_ru`), `notes_ru` — пояснения
к тому, что изменилось (самочувствие, сокращение, перенос), `substitutions` — журнал замен,
`sets` — уже записанные подходы. Каждое упражнение несёт `planned_slug` — ячейку плана,
которую оно занимает: прогрессия идёт по ячейке, а не по конкретному упражнению.

**Подходы.** Главный эндпоинт по частоте вызовов. Клиент копит подходы на устройстве и шлёт
пачкой (до 200) каждые несколько секунд, с ретраями. Каждый подход — с `client_uuid`,
`exercise_slug`, `set_index`, `reps`, `performed_at`, при необходимости `side`
(`both`/`left`/`right`), `weight_kg`, `added_weight_kg`, `rir`, `is_warmup`. Повторная
отправка того же uuid — не ошибка, а no-op. Ответ: `accepted` (uuid), `records` — побитые
этой пачкой личные рекорды, `total_tonnage_kg`. В закрытую тренировку подходы не
принимаются (422).

**Замена.** `{"exercise_slug": "...", "reason": "equipment_busy|pain|too_hard|too_easy|disliked"}`.
422, если заменить нечем. Причина `weather` для одного упражнения не принимается.

**Сокращение.** `{"minutes_left": 15}`. Разминка не режется, основные движения остаются,
в крайнем случае теряя подходы.

**Перенос.** `{"location_id": "..."}`. Те же паттерны под инвентарь нового места; упражнения,
по которым уже есть подходы, не трогаются; что заменить нечем — выпадает с пояснением в
`notes_ru`. Каждая замена пишется в `substitutions` с причиной `weather`.

## Прогресс

```
GET /progress/summary               серия недель, неделя (тренировки, тоннаж), рекорды «рядом»,
                                    число дисбалансов сторон
GET /progress/patterns/{code}       точка на тренировку: ступень лестницы и лучший результат
GET /progress/exercises/{slug}      точка на тренировку: лучший результат, макс. вес, тоннаж
GET /progress/tonnage               ?period=week|month&pattern=…
GET /progress/records               личные рекорды, новые сверху
GET /progress/balance               односторонние упражнения с разницей сторон больше 15%
GET /progress/skills                дерево навыков: статус, цель, предусловия, подводящие
PUT /progress/skills/{slug}         {"achieved": true|false} — ручная отметка
```

Результат (`ResultRead`) бывает трёх видов: `est_1rm` — расчётный максимум в кг, `reps`,
`seconds`. Навыки пересчитываются из истории при каждом чтении; освоенный навык остаётся
освоенным. Ручная отметка нужна навыкам без собственного упражнения в справочнике
(`goal: null`); снять отметку с навыка, засчитанного по тренировкам, нельзя (422).

## Тело

```
GET    /body/metrics?from=&to=       замеры (новые сверху) + weight_trend — среднее за 7 дней
POST   /body/metrics                 вес и/или обхваты; хотя бы одно значение
DELETE /body/metrics/{id}
GET    /body/photos                  фото со ссылками на просмотр (действуют 15 минут)
POST   /body/photos/upload-url       {"angle": "front|side|back", "content_type": "image/…"}
DELETE /body/photos/{id}             удаляет и запись, и файл
```

Фото загружаются мимо бэкенда: `upload-url` создаёт запись и возвращает форму presigned POST
(`url` + `fields`). Клиент отправляет её multipart-запросом, файл — последним полем.
Политика формы ограничивает размер (до 15 МБ) и тип (`image/*`). Если загрузка не удалась,
клиент удаляет пустую запись.

## Погода

```
GET /weather/forecast?location_id=     прогноз на ближайшие часы для уличного места
```

Ответ: `verdict` — `move_indoors`, `concerns` (`rain`/`snow`/`wind`/`cold`/`heat`), `hints`
(`frost`/`warm`), `text_ru`, границы окна; `hours` — 12 часов вперёд;
`indoor_location_id` — куда переносить. `verdict: null`, если прогноз не покрывает окно.
Место без координат или не уличное — 422, провайдер недоступен — 503.

Бэкенд проксирует Open-Meteo и кеширует ответ в Redis по координатам, округлённым до ~1 км, и
часу — на 30 минут. Пороги — в [03-engine.md](03-engine.md#8-погода).

## Экспорт

```
GET /export/all        полный дамп данных пользователя: JSON-файл вложением
```

Профиль, уровни, места с инвентарём, программы, все тренировки с подходами, рекорды, замеры,
фото (ссылками на 15 минут), прогресс навыков. `format_version` — версия формата файла.

## Генерация типов для фронта

FastAPI отдаёт OpenAPI-схему на `/api/v1/openapi.json`. Фронтенд генерирует из неё
TypeScript-типы командой `corepack pnpm gen:api`. Руками типы ответов API не пишутся. Если
схема изменилась — сначала перегенерировать, потом править код. CI проверяет, что
`frontend/src/api/schema.d.ts` совпадает со схемой.
