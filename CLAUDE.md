# Self Forge

Веб-приложение для силовых тренировок дома и на уличных площадках. Человек указывает
своё оборудование, цель и доступные дни — приложение собирает программу и ведёт по ней,
обеспечивая прогрессию даже при фиксированном весе снарядов.

Домен и продуктовые решения описаны в `docs/`. Читай их перед работой над задачей:

| Файл | О чём |
|---|---|
| `docs/00-product.md` | Концепция, аудитория, границы MVP, принципы |
| `docs/01-domain.md` | Паттерны движения, оборудование, лестницы сложности, цели |
| `docs/02-data-model.md` | Сущности, связи, ключевые поля |
| `docs/03-engine.md` | Движок генерации программ и прогрессии |
| `docs/04-api.md` | Контракт API, соглашения |
| `docs/05-frontend.md` | Стек фронта, структура, дизайн-система, экран тренировки |
| `docs/06-roadmap.md` | Порядок работ вертикальными срезами |
| `docs/07-deploy.md` | Прод на VPS за хостовым nginx, бэкапы, восстановление |

## Структура репозитория

```
backend/     FastAPI, Python 3.12+, uv
frontend/    React + TypeScript, Vite, pnpm
deploy/      Прод-стек: compose, конфиг nginx, скрипты деплоя и бэкапов
docs/        Спецификации (источник истины по домену)
```

## Стек

**Бэкенд:** FastAPI, Pydantic v2, SQLAlchemy 2.0 (async), PostgreSQL, Alembic, Redis,
JWT с ротацией refresh-токенов, uv, ruff, mypy (strict), pytest.

**Фронтенд:** React 19, TypeScript (strict), Vite, TanStack Router, TanStack Query,
Zustand, Tailwind CSS v4, shadcn/ui, React Hook Form + Zod, Recharts, Biome, Vitest.

**Связь типов:** типы API генерируются из OpenAPI-схемы FastAPI через `openapi-typescript`.
Руками TS-типы для ответов API не пишутся никогда.

## Команды

```
# бэкенд (из backend/)
make dev            запуск с автоперезагрузкой
make lint           ruff check + ruff format --check
make typecheck      mypy strict
make test           pytest
make migrate        alembic upgrade head
make revision m=""  новая миграция

# фронтенд (из frontend/)
pnpm dev
pnpm build
pnpm lint
pnpm typecheck
pnpm test
pnpm gen:api        перегенерировать типы из OpenAPI бэкенда
```

## Правила работы

**Git.** В этом проекте коммить сам, не спрашивая разрешения на каждый коммит.

Коммиты короткие и осознанные: один коммит — одно законченное изменение. Не сваливай
весь этап в один коммит и не коммить нерабочее состояние. Прогоняй `lint`, `typecheck`
и `test` до коммита, а не после.

Сообщения — на английском, в повелительном наклонении, до 72 символов в заголовке.
Тело добавляется только когда нужно объяснить причину решения, а не пересказать диффы.
Формат Conventional Commits (`feat:`, `fix:`, `refactor:`, `test:`, `chore:`, `docs:`).

**Категорически нельзя** в сообщении коммита: упоминания Claude, строк `Co-Authored-By`,
текстов вроде «Generated with» — ни в каком виде.

Всё остальное в git делаю не я: ветки, `push`, `rebase`, `merge`, работа с удалёнными
репозиториями, `git reset --hard`, любое переписывание истории и всё, что удаляет данные.
Если такое нужно — выведи готовую команду для копирования в терминал
(shell: fish, macOS) и объясни, что она сделает.

**Язык.** Общение в чате — на русском. Код, имена сущностей, коммиты, комментарии в коде —
на английском. Пользовательские тексты интерфейса — на русском.

**Движок — чистый.** Логика генерации программ и прогрессии живёт в `backend/app/engine/`
и не импортирует SQLAlchemy, FastAPI, Redis. Вход и выход — dataclass/pydantic-модели.
Всё, что туда попадает, покрывается юнит-тестами. Это ядро продукта.

**Слои бэкенда.** `api/v1 → services → repositories → models`. Наружу ORM-объекты не
отдаются, только схемы из `schemas/`.

**Миграции.** Любое изменение модели сопровождается миграцией Alembic. Справочные данные
(упражнения, паттерны) в миграции не кладутся — для них есть идемпотентный seed-скрипт.

**Тесты.** Бэкенд тестируется на настоящем PostgreSQL (не SQLite), потому что модель
данных опирается на JSONB. Движок — табличные тесты с большим числом сценариев.

**Безопасность и здоровье.** Приложение даёт тренировочные рекомендации. Не генерируй
медицинские советы, не обещай сроки результата, не предлагай темп снижения веса быстрее
1% массы тела в неделю и не опускай расчёт калорий ниже безопасного минимума.
Текстовые формулировки не строятся на стыде за пропуски.

## Порядок работы над задачей

1. Прочитать относящиеся к задаче файлы `docs/`.
2. Если спецификация чего-то не покрывает — спросить, а не домысливать. Спорные
   продуктовые решения не принимаются молча.
3. Сделать вертикальный срез: миграция → модель → сервис → эндпоинт → типы → экран.
4. Прогнать `lint`, `typecheck`, `test` с обеих сторон.
5. Закоммитить результат по правилам выше.
